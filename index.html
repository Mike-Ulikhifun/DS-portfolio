Project One: Predicting Housing Prices in Buenos Aires (Argentina's Capital and Largest City) with Linear Regression

This project created a solid basis for supervised machine learning-based flat price prediction in Buenos Aires. Raw real estate data with uneven market segmentation, missing values, outliers, redundant columns, and categorical variables that regression models could not use directly presented the first challenge. By merging the data, limiting the target market, cleaning observations, engineering geographical features, eliminating variables that can result in data leakage, encoding neighbourhood information, and establishing a train-test split, these problems were resolved. This procedure produced a structured dataset with 6,247 observations from 43,029 raw listings. The creation of a repeatable and rationally sound data preparation procedure that facilitated trustworthy model training and assessment was the main accomplishment. Predictive models were trained and tested on previously unknown flat listings using the prepared dataset. The accuracy of price forecasts and their potential use in assisting with real estate appraisal and decision-making were then evaluated by evaluating the model's performance.

Objective Build a model that generalises well to unseen listings and identify the most predictive property features. What I Did
  1. Data Loading and Cleaning: Imported, merged and cleaned listing data from multiple CSV files, handling missing values, outliers and type conversions.
  2. Baseline Model Development: Built a baseline linear regression model in scikit-learn.
  3. Model Evaluation: Evaluated RMSE, MAE and R² on training and test sets.
  4. Regularisation: Applied Ridge and Lasso regularisation with standardised features to reduce overfitting on high-cardinality encoded data.
  5. Model Comparison and Selection: Compared models in a structured evaluation table and selected the best-generalising one.

Results MODEL COMPARISON TABLE ============================================================ Train_RMSE Test_RMSE Gap Model Baseline 59700.25 57576.13 -2124.12 Linear Regression 34200.43 33088.37 -1112.06 Ridge (CV-tuned) 34203.95 33071.27 -1132.68 Lasso (CV-tuned) 34203.20 33069.18 -1134.01 Selected Model: Lasso Regression (CV-Tuned) Why: Lasso achieved the lowest test RMSE of $33,069.18, slightly outperforming Ridge and Linear Regression. Since all three predictive models performed almost identically, Lasso is a reasonable choice because it combined strong predictive performance with feature selection and interpretability. Lasso reduced the test RMSE by approximately 42.6% compared with the baseline, showing that the selected features provide useful information for predicting property prices.

What I Learnt from the Model
  • Test RMSE matters most: I should evaluate models on unseen data rather than relying only on training performance.
  • Regularisation helps control overfitting: Ridge and Lasso penalise large coefficients, helping models generalise to new properties.
  • Model performance was nearly identical: The differences between Linear Regression, Ridge, and Lasso were very small, so Lasso's numerical advantage does not prove that it is significantly better.
  • Property size is the strongest predictor: The surface_covered_in_m2 feature had the largest positive coefficient, indicating that property size is an important predictor of price.
  • Interpretability matters: Lasso can set some coefficients to zero, simplifying a model. However, in this experiment, it eliminated only 1 of 59 features (1.7%), so its sparsity advantage was modest.
  • The model has limitations: Residual analysis suggests that prediction errors increase for more expensive properties. The model may therefore be less reliable for luxury apartments.
Key Takeaway The most important lesson was that the best model isn't necessarily the one with the lowest error. We must also consider interpretability, generalisation, complexity, and the consequences of prediction errors. For this project, I practically selected Lasso Regression (CV-Tuned) because it achieved the lowest test RMSE while offering some feature-selection benefits. However, before deploying it in production, I investigated the larger errors for expensive properties and compared its performance with nonlinear models. Project Two: Time Series Modelling of Air Quality in Nairobi (Kenya's Capital and Largest City)

The problem addressed was the increasing volume of air quality data in Nairobi and the need to analyse PM2.5 pollution over time. The issues were the growing volume of Nairobi's air quality data and the need to assess PM2.5 pollution over time. Sensor readings are time-dependent, meaning past pollution levels may help predict future levels. Therefore, time series analysis is necessary to identify trends, patterns, and potential changes in air quality. MongoDB Atlas Database was selected because it stores large volumes of time-stamped data, supports flexible document structures, enables efficient time-range queries through timestamp indexing, and can scale horizontally as data grows. Unlike Excel, which has a row limit, MongoDB can accommodate expanding datasets. Its flexible schema also allows sensors to report different measurements without requiring database restructuring. The project contained 10,000 documents from ten Nairobi sensors, providing a foundation for analysis. Data wrangling was carried out using Python, PyMongo, and pandas to extract PM2.5 readings from the MongoDB database, identify and handle missing values, convert timestamps into datetime format, and arrange observations in chronological order. The resulting clean and structured time-series dataset was prepared for subsequent predictive modelling and the analysis of air quality trends in Nairobi. Predictive modelling was conducted using linear regression with lag features, whereby previous PM2.5 readings were used to predict future pollution levels. Model performance was evaluated using Mean Absolute Error (MAE), Root Mean Squared Error (RMSE), and the coefficient of determination (R²), with the results compared against a persistence baseline. The modelling process provided a basis for assessing predictive accuracy, identifying air pollution patterns, and supporting evidence-based air quality management in Nairobi.

Objective Forecast future air quality values and compare model families on held-out future data. What I Did
  • Queried and prepared time-stamped data from a MongoDB database
  • Constructed lagged features and applied linear regression with time-aware train/test splits
  • Fit and interpreted AR(p) models for temporal forecasting
  • Compared AR and ARMA models and evaluated forecast performance on held-out future data

Project Three: Predicting Earthquake Damage in Nepal with Classification Models

In April 2015, A major earthquake hit Nepal. Classifying building damage after the Nepal earthquake was needed to support humanitarian decision-making. This project addressed the problem of managing and analysing large, interconnected datasets from Nepal’s 2015 Gorkha earthquake. The four related tables contained building structures, damage assessments, household demographics, and geographical information. Analysing these separately made it difficult to identify damage patterns, assess building vulnerability, and understand the relationship between household characteristics and earthquake impacts. The main objective was to learn how relational databases support efficient data management, accurate analysis, and reliable data preparation for machine learning. Issues identified included data duplication, inconsistencies, incorrect table joins, missing relationships, and slow analytical queries. These challenges were addressed through database normalisation, primary and foreign keys, SQL queries, and appropriate use of INNER JOIN and LEFT JOIN. SQLite was used for structured storage and transactional operations, while DuckDB provided faster analytical queries directly from CSV files. Practical activities I carried out included connecting to SQLite, querying tables, counting buildings, identifying foundation types, filtering Gorkha data, comparing database performance, and developing a reusable wrangle_nepal_data() function. The function combined relevant datasets, selected building features, and created a binary severe-damage target. The prepared Gorkha dataset contained 70,836 buildings, with approximately 64.26% experiencing severe damage, providing a foundation for subsequent machine learning and earthquake damage prediction

Objective: Predict damage severity from building data and explain results in terms of real-world response.

What I Did

  • Assembled a modelling dataset from a relational SQLite database using SQL joins to combine relevant data from multiple tables.
  • Built logistic regression classifiers and evaluated their performance using accuracy, precision, recall, and confusion matrices.
  • Trained decision tree classifiers and compared their predictive performance and interpretability with logistic regression models.
  • Interpreted statistical findings and connected model results to real-world decision-making in humanitarian response, particularly earthquake damage assessment and building vulnerability identification.

Humanitarian Interpretation: These findings suggest that building characteristics, such as age, foundation type, and structural features, can help identify buildings vulnerable to severe earthquake damage. Logistic regression may therefore support humanitarian organisations and local authorities in prioritising building inspections, allocating limited resources, and planning reconstruction efforts. Although the decision tree performed slightly worse, its interpretable decision rules may help explain risk factors to decision-makers. However, accuracy alone is insufficient for determining which model is most suitable for humanitarian intervention. Recall for severely damaged buildings is particularly important because missed high-risk buildings could delay essential assistance. Therefore, precision, recall, and confusion matrices should also be examined before deployment. Ultimately, these models should complement engineering inspections and local assessments rather than replace professional judgement in disaster response and recovery.

Tools: Python, SQL, SQLite, pandas, DuckDB, scikit-learn, wrangle_nepal_data() function

Project Four:

Ask a home buyer to describe their dream house, and they probably won't begin with the height of the basement ceiling or the proximity to an east-west railroad. But this playground competition's dataset proves that much more influences price negotiations than the number of bedrooms or a white-picket fence. With 79 explanatory variables describing (almost) every aspect of residential homes in Ames, Iowa, this competition challenges you to predict the final price of each home. The Ames Housing Dataset is a collection of residential property sales data from Ames, Iowa, covering homes sold between 2006 and 2010. It was compiled by Dean De Cock in 2011 from the city’s property records and contains 79 explanatory variables describing housing characteristics, including location, size, quality, condition, and amenities. The dataset supports predictive analytics and machine learning for property valuation. Real estate professionals can use similar models to estimate prices, guide investment decisions, improve pricing strategies, assess market trends, and help buyers and sellers make informed decisions. The dataset aims to develop models that accurately predict residential property sale prices based on their features. It addresses the challenge of estimating property values objectively in a market where prices depend on multiple factors. I was to predict residential sale prices (SalePrice) for homes in Ames, Iowa, using the Kaggle House Prices: Advanced Regression Techniques dataset. It has 1,460 training rows, 1,459 test rows and 79 features.

objective The goal is to find the most accurate regressor and generate a competition submission.

What I did

  • Explored the data: Reviewed missing values, duplicates (none), and target statistics. SalePrice is right-skewed (skewness 1.88, kurtosis 6.54).
  • Built a leak-safe preprocessing pipeline: Used a ColumnTransformer with median imputation and scaling for 36 numeric features. For 43 categorical features, it used most-frequent imputation and one-hot encoding with handle_unknown='ignore'.
  • Compared four models: Trained Linear Regression, Ridge (α = 10), Random Forest (300 trees), and Gradient Boosting (300 estimators, depth 3) on an 80/20 split with random_state = 42.
  • Evaluated on held-out data: Scored every model on the 292-row validation set using RMSE and R².
  • Produced predictions: Refit the best model on all 1,460 rows, predicted the test set, and exported submission_alt.csv.

Results Model RMSE ($) R² Linear Regression 29,474 0.887 Ridge Regression 30,646 0.878 Random Forest 28,398 0.895 Gradient Boosting 25,897 0.913 Each score came from predicting the same validation split and comparing against actual prices. Gradient Boosting had the lowest error and highest R², so it was selected.

Discussion Gradient Boosting beat Random Forest by about $2,500 RMSE and the linear models by roughly $3,600–4,700. That suggests nonlinear patterns and feature interactions matter in this data. Ridge scored slightly worse than plain Linear Regression, so an untuned α=10 added no value here. Why Gradient Boosting? It builds trees sequentially, with each tree correcting the previous one’s errors. That handles mixed feature types, nonlinear effects and interactions without manual feature engineering. The data-driven comparison confirmed it: it won on both metrics. Key Takeaways 1. Wrapping preprocessing and model in one Pipeline keeps validation honest and the workflow reproducible. 2. Ensemble methods outperformed linear models on this tabular problem. 3. Several improvements would strengthen the project:

  • Log-transform the target: The notebook’s own EDA shows heavy skew, but the target is modelled raw.
  • Add cross-validation: It currently uses a single split, so the ranking could shift with a different seed.
  • Tune hyperparameters: Ridge’s alpha and Gradient Boosting’s settings were never tuned.
  • Engineer features: Totals such as combined square footage or bathrooms were not created.
  • Fix the Gradient Boosting comment: It wrongly mentions L2 regularisation.
4. No Kaggle leaderboard score is recorded, so real test performance is unverified. What the Model Solved It delivers a working end-to-end pricing estimator: raw, messy housing data in, predictions out. On unseen validation homes, it explains about 91% of price variance, with a typical error near $26K on homes averaging about $181K. It produced a ready-to-submit Kaggle file and a solid baseline to build on. Tools Python 3, pandas, NumPy, scikit-learn, Jupyter Notebook (ipykernel), Category_encoders, Matplotlib
