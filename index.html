Project One: Predicting Housing Prices in Buenos Aires (Argentina's Capital and Largest City) with Linear Regression

This project created a solid basis for supervised machine learning-based flat price prediction in Buenos Aires. Raw real estate data with uneven market segmentation, missing values, outliers, redundant columns, and categorical variables that regression models could not use directly presented the first challenge. By merging the data, limiting the target market, cleaning observations, engineering geographical features, eliminating variables that can result in data leakage, encoding neighbourhood information, and establishing a train-test split, these problems were resolved. This procedure produced a structured dataset with 6,247 observations from 43,029 raw listings. The creation of a repeatable and rationally sound data preparation procedure that facilitated trustworthy model training and assessment was the main accomplishment. Predictive models were trained and tested on previously unknown flat listings using the prepared dataset. The accuracy of price forecasts and their potential use in assisting with real estate appraisal and decision-making were then evaluated by evaluating the model's performance.

Objective Build a model that generalises well to unseen listings and identify the most predictive property features. What I Did
  1. Data Loading and Cleaning: Imported, merged and cleaned listing data from multiple CSV files, handling missing values, outliers and type conversions.
  2. Baseline Model Development: Built a baseline linear regression model in scikit-learn.
  3. Model Evaluation: Evaluated RMSE, MAE and R² on training and test sets.
  4. Regularisation: Applied Ridge and Lasso regularisation with standardised features to reduce overfitting on high-cardinality encoded data.
  5. Model Comparison and Selection: Compared models in a structured evaluation table and selected the best-generalising one.

Since all three predictive models performed almost identically, Lasso is a reasonable choice because it combined strong predictive performance with feature selection and interpretability. Lasso reduced the test RMSE by approximately 42.6% compared with the baseline, showing that the selected features provide useful information for predicting property prices. What I Learnt from the Model
  • Test RMSE matters most: I should evaluate models on unseen data rather than relying only on training performance.
  • Regularisation helps control overfitting: Ridge and Lasso penalise large coefficients, helping models generalise to new properties.
  • Model performance was nearly identical: The differences between Linear Regression, Ridge, and Lasso were very small, so Lasso's numerical advantage does not prove that it is significantly better.
  • Property size is the strongest predictor: The surface_covered_in_m2 feature had the largest positive coefficient, indicating that property size is an important predictor of price.
  • Interpretability matters: Lasso can set some coefficients to zero, simplifying a model. However, in this experiment, it eliminated only 1 of 59 features (1.7%), so its sparsity advantage was modest.
  • The model has limitations: Residual analysis suggests that prediction errors increase for more expensive properties. The model may therefore be less reliable for luxury apartments.
Key Takeaway The most important lesson was that the best model is not necessarily the one with the lowest error alone. We must also consider interpretability, generalisation, complexity, and the consequences of prediction errors. For this project, I practically selected Lasso Regression (CV-Tuned) because it achieved the lowest test RMSE while offering some feature-selection benefits. However, before deploying it in production, I investigated the larger errors for expensive properties and compared its performance with nonlinear models. Project Two: Time Series Modelling of Air Quality in Nairobi (Kenya's Capital and Largest City)

The problem addressed was the increasing volume of air quality data in Nairobi and the need to analyse PM2.5 pollution over time. The issues were the growing volume of Nairobi's air quality data and the need to assess PM2.5 pollution over time. Sensor readings are time-dependent, meaning past pollution levels may help predict future levels. Therefore, time series analysis is necessary to identify trends, patterns, and potential changes in air quality. MongoDB Atlas Database was selected because it stores large volumes of time-stamped data, supports flexible document structures, enables efficient time-range queries through timestamp indexing, and can scale horizontally as data grows. Unlike Excel, which has a row limit, MongoDB can accommodate expanding datasets. Its flexible schema also allows sensors to report different measurements without requiring database restructuring. The project contained 10,000 documents from ten Nairobi sensors, providing a foundation for analysis. Data wrangling was carried out using Python, PyMongo, and pandas to extract PM2.5 readings from the MongoDB database, identify and handle missing values, convert timestamps into datetime format, and arrange observations in chronological order. The resulting clean and structured time-series dataset was prepared for subsequent predictive modelling and the analysis of air quality trends in Nairobi. Predictive modelling was conducted using linear regression with lag features, whereby previous PM2.5 readings were used to predict future pollution levels. Model performance was evaluated using Mean Absolute Error (MAE), Root Mean Squared Error (RMSE), and the coefficient of determination (R²), with the results compared against a persistence baseline. The modelling process provided a basis for assessing predictive accuracy, identifying air pollution patterns, and supporting evidence-based air quality management in Nairobi.

Objective Forecast future air quality values and compare model families on held-out future data. What I Did
  • Queried and prepared time-stamped data from a MongoDB database
  • Constructed lagged features and applied linear regression with time-aware train/test splits
  • Fit and interpreted AR(p) models for temporal forecasting
  • Compared AR and ARMA models and evaluated forecast performance on held-out future data

  • Lowest prediction error: Its MAE of 7.94 means its predictions differ from actual values by an average absolute amount of 7.94 units, assuming the target's original units.
  • Combines two approaches: The AR(2) component uses the previous two observations, while the MA(1) component models the influence of the previous period's forecast error.
  • Improves on the baseline: Its MAE is approximately 14.3% lower than the baseline MAE of 9.26.
  • Captures temporal patterns: Combining autoregressive and moving-average components can capture patterns that a simple persistence model or a basic linear regression may miss.

What I Learnt

  • Simple baselines are important: The persistence model provides a benchmark to determine whether more advanced models add value.
  • Combining model components can improve predictions: ARMA incorporates both past observations and past forecast errors.
  • MAE makes model comparison practical: Lower MAE means smaller average absolute prediction errors.
  • Actual results matter: Because the Linear Regression and AR Model values are estimates, we should compute their actual MAE values before making a definitive comparison across all four models.

Project Three: Predicting Earthquake Damage in Nepal with Classification Models

This project addressed the problem of managing and analysing large, interconnected datasets from Nepal’s 2015 Gorkha earthquake. The four related tables contained building structures, damage assessments, household demographics, and geographical information. Analysing these separately made it difficult to identify damage patterns, assess building vulnerability, and understand the relationship between household characteristics and earthquake impacts. The main objective of this project was to learn how relational databases support efficient data management, accurate analysis, and preparation of reliable data for machine learning. Issues identified included data duplication, inconsistencies, incorrect table joins, missing relationships, and slow analytical queries. These challenges were addressed through database normalisation, primary and foreign keys, SQL queries, and appropriate use of INNER JOIN and LEFT JOIN. SQLite was used for structured storage and transactional operations, while DuckDB provided faster analytical queries directly from CSV files. Practical activities I carried out while working on this project included connecting to SQLite, querying tables, counting buildings, identifying foundation types, filtering Gorkha data, comparing database performance, and developing a reusable wrangle_nepal_data() function. The function combined relevant datasets, selected building features, and created a binary severe-damage target. The prepared Gorkha dataset contained 70,836 buildings, with approximately 64.26% experiencing severe damage, providing a foundation for subsequent machine learning and earthquake damage prediction
